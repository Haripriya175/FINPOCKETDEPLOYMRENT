# FinPocket Comprehensive Threat Model

This document outlines FinPocket's STRIDE-based threat modeling, analyzing potential security threats, impacts, architectural mitigations, and residual risks.

| Threat ID | Threat Category | Threat Description | Potential Impact | Architectural Mitigation | Residual Risk |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **TH-01** | *Spoofing / Stolen Token* | Adversary steals or intercepts a JWT access token via client breach or proxy sniffing. | Unauthorized access to user financial dashboard and transaction history. | Short-lived access tokens (15 minutes), strict HTTPS/TLS termination, secure storage on client device, device-bound sessions. | Valid token grants access until 15-minute expiry unless revoked. |
| **TH-02** | *Spoofing / Refresh Token Reuse* | Adversary intercepts a refresh token and attempts to generate new access tokens. | Long-term account takeover. | Refresh tokens are hashed at rest, single-use rotated, and automatic reuse detection revokes all tokens in the session family. | Attacker using refresh token before legitimate user forces re-authentication for user. |
| **TH-03** | *Tampering / Idempotency & Replay* | Network jitter or attacker replays a payment execution request. | Double payment or unintended financial deduction. | Idempotency key tracking in atomic transactions. Duplicate keys return cached previous result without re-executing deduction. | Keys expire after 24 hours; client must provide unique keys. |
| **TH-04** | *Tampering / Race Conditions* | Simultaneous payment requests exploit race conditions to spend more than available balance. | Negative account balance, overdraft, financial loss. | Transaction isolation with atomic row updates checking balance constraints directly inside SQL transaction. | Handled via SQLite serialize or PostgreSQL `SELECT FOR UPDATE`. |
| **TH-05** | *Information Disclosure / IDOR* | Malicious authenticated user queries another user's financial accounts, bills, or transactions. | Privacy breach, exposure of financial balances and PII. | Authenticated user ID is derived strictly from JWT payload. All SQL queries enforce `WHERE user_id = ?`. Client parameters are disregarded. | Zero IDOR risk on verified endpoints. |
| **TH-06** | *Information Disclosure / Error Leakage* | Database error or unexpected server exception reveals SQL query, stack trace, or table structure. | Server reconnaissance for vulnerability targeting. | Centralized error handler catches all exceptions, logs details internally with `requestId`, and returns sanitized `{ code, message, requestId }`. | None in production mode. |
| **TH-07** | *Information Disclosure / Sensitive Logging* | Passwords, PINs, bank account numbers, or tokens get recorded in plain server log files. | Credential compromise via log access or aggregation services. | Custom request tracking middleware scans and redacts sensitive field patterns (`password`, `pin`, `token`, `secret`, `authorization`, `card`). | Unformatted ad-hoc debug console logs must be avoided in codebase. |
| **TH-08** | *Denial of Service / Brute Force* | Adversary executes high-frequency credential stuffing or password reset requests. | Account lockout, resource exhaustion, CPU spike. | Multi-tier rate limiting on `/auth/login` (15 req/15m) and generic endpoints. Constant-time comparison for password hashing. | Distributed botnets requiring upstream WAF (Cloudflare/AWS Shield). |
| **TH-09** | *Elevation of Privilege / AI Abuse* | Attacker prompts AI assistant to execute payments, transfer funds, or reveal other users' records. | Unauthorized money movement or data leakage. | AI operates strictly via a read-only tool allowlist dispatcher. AI has zero access to payment mutation tools. User scope is hardcoded from session. | Prompt injection cannot cause mutations due to lack of write tools. |
| **TH-10** | *Security Misconfiguration / Demo Leak* | Production deployed with demo auto-login or mock provider enabled. | Insecure login bypass or fake financial data in production. | `loadAndValidateConfig()` enforces fail-closed startup: `NODE_ENV=production` fails immediately if demo mode, mock provider, or weak secrets are detected. | Production deployment pipeline must ensure proper environment variables. |
